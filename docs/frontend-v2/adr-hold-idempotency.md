# Mini ADR: Seat Hold Command Idempotency

- **Status:** Proposed (Requires Human Approval Gate #1 Decision)
- **Context:** VeloBus Booking Context — `POST /api/v1/bookings/hold`
- **Date:** 2026-11-26
- **Authors:** Core Architecture Team & AI Engineering Assistant

---

## 1. Context and Problem Statement

When a customer initiates seat reservation (`POST /api/v1/bookings/hold`), network timeouts, client disconnects, or browser retries can create ambiguous mutation states.
Currently, `HoldSeatUseCase` acquires Redis distributed locks via `SeatLockRepository.acquireLocks` and writes a `Booking` aggregate with status `HELD` to the relational database.
If a request times out from the client's perspective after Redis locks are acquired or after DB commits, subsequent retries by the user could:
1. Fail with `SEAT_ALREADY_RESERVED` because the seats are already locked by the prior request.
2. Create duplicate booking records if seat keys differ or if timeout recovery is not strictly idempotent.
3. Leave the frontend unable to authoritatively distinguish between an interrupted successful hold and a genuine conflict.

We need an architectural decision on how to achieve authoritative request correlation and hold command idempotency across Booking Context.

---

## 2. Options Considered

### Option A: Persistent Database Table (`idempotency_keys`)
- **Design:** Dedicated table `idempotency_keys` storing `(key, context, request_hash, response_payload, status, expires_at)`.
- **Workflow:**
  1. Transaction begins; attempts to insert idempotency key with status `IN_PROGRESS`.
  2. If unique key violation: read record. If `COMPLETED`, replay stored `response_payload`. If `IN_PROGRESS`, return 409 Conflict.
  3. Execute `HoldSeatUseCase` and serialize `BookingResponse` into `response_payload`. Update status to `COMPLETED`.
- **Pros:**
  - Generalized across all mutation commands (bookings, payments, refunds, withdrawals).
  - Exact payload replay guarantee.
  - Durable across server restarts.
- **Cons:**
  - Extra database writes (INSERT + UPDATE) on every reservation command.
  - Requires database migration and cleanup cron/job to prune expired keys.
  - Higher latency overhead on high-throughput seat holding.

### Option B: Request ID on Booking Entity with Unique Constraint (Recommended)
- **Design:** Add an optional column `client_request_id VARCHAR(64)` to the existing `bookings` table with a partial/unique index `(user_id, client_request_id) WHERE status = 'HELD'`.
- **Workflow:**
  1. Client sends header `Idempotency-Key` or payload property `clientRequestId` (UUID generated by client before mutation).
  2. `HoldSeatUseCase` queries `bookingRepository.findByUserIdAndClientRequestId(userId, clientRequestId)`.
  3. If existing active HELD booking found: return existing `BookingResponse` immediately (idempotent replay).
  4. If not found: proceed with Redis lock acquisition and insert new `Booking` with `client_request_id`.
  5. If concurrent race hits unique constraint on DB commit: catch `DataIntegrityViolationException`, reload the existing booking, and return it.
- **Pros:**
  - **Smallest reliable footprint**: Uses existing domain aggregate and table without creating generic table sprawl.
  - Zero performance penalty on read path; single indexed lookup.
  - Perfect consistency: request ID lifecycle is transactionally tied to the `Booking` aggregate itself.
  - Clean auditability: directly traces which client mutation produced which booking.
- **Cons:**
  - Requires a nullable DB migration (`ALTER TABLE bookings ADD COLUMN client_request_id VARCHAR(64)`).
  - Specific to Booking aggregate (cannot be reused for non-booking mutations without adding columns to other tables).

### Option C: Redis-Only Idempotency Key (`SETNX` + Cached Reference)
- **Design:** Redis key `idempotency:hold:{userId}:{clientRequestId}` storing `{ bookingReference, status }` with TTL = 10 minutes.
- **Workflow:**
  1. Client sends `clientRequestId`.
  2. Service runs `SET idempotency:hold:{userId}:{clientRequestId} PENDING NX EX 60`.
  3. If key exists: wait/poll or read cached booking reference and fetch booking from DB.
  4. After DB commit, update key to `{ bookingReference: 'VB-...', status: 'COMPLETED' }` with 10 min TTL.
- **Pros:**
  - Zero database schema changes required.
  - Ultra-fast execution via in-memory Redis.
- **Cons:**
  - **Dual-write failure modes:** If node crashes between Redis lock acquisition/DB write and caching, Redis key may be inconsistent with DB.
  - Redis eviction or restart during holds loses correlation metadata.
  - Lacks ACID durability guarantees compared to relational storage.

## 3. Comparison Matrix

| Criteria | Option A (Idempotency Table) | Option B (Request ID on Booking) | Option C (Redis-Only) |
| :--- | :--- | :--- | :--- |
| **Distributed Consistency** | Strong (ACID DB transaction) | Strong (ACID DB transaction) | Eventual / Vulnerable to node crash |
| **Failure Modes** | Key cleanup required; table bloat | Handled by unique index rollback | Orphaned keys; inconsistent states |
| **Implementation Complexity** | Medium-High (General filter/entity) | Low-Medium (1 column + domain field) | Medium (Lua / multi-step cache orchestration) |
| **Performance Overhead** | +2 DB round trips per hold | +0 to 1 indexed query | Minimal (~1-2 ms Redis command) |
| **Schema Migration Required** | Yes (New table) | Yes (1 nullable column + index) | No |
| **Architectural Scope** | System-wide framework | Booking Context specific | Infrastructure cache only |

---

## 4. Recommendation & Gate Decision

### Recommendation: Option B (Request ID on Booking Entity)
Option B is the smallest, safest, and most resilient solution. It ties the idempotency token directly to the domain aggregate's transaction boundary, eliminating split-brain states between Redis and PostgreSQL.
